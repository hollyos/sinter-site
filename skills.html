Skills

48 skills. Each carries an explicit trigger and an explicit non-trigger: with this many, two skills that both fire on "review this" would mean neither is reliable.

Always on4

Resident on every task. The router picks the depth, clarify resolves a thin request, principles holds the invariants, prose-register sets the output register.

clarify

Use at the very start of a task when the request is too thin to act on safely - a few words, a vague goal, an ambiguous pronoun, or a known unknown that changes the implementation. Resolve intent before the router picks a lane. Prefer inferring from context; ask only when a wrong guess is expensive to undo.

Fires on "fix the thing", "make it better", "add that", "it's broken", and any request whose success criteria you cannot state back.

Not for when the request is already specific, or for design exploration of a feature that clearly needs building - that is `brainstorming`.

principles

The invariants and the simplicity ladder that govern every Sinter task. Use on ANY coding work - writing, fixing, refactoring, reviewing, designing, choosing a dependency. Also use when the user says "ponytail", "be lazy", "yagni", "simplest thing", "do less", or complains about over-engineering, bloat, or unnecessary dependencies.

Not for non-coding requests.

References ladder

Origin Adapted from Ponytail (MIT) and directives by @hollyos.

prose-register

Output register and punctuation. Sets how tersely Sinter writes and which characters it types, without changing what it says. Use on every response, and when the user says "be brief", "terse", "less tokens", "stop explaining", "no em dashes", "plain punctuation", or sets /sinter:mode prose. Governs phrasing and characters only - never removes a tradeoff, a caveat, or a piece of technical substance.

Not for to decide how much code to write; that is `principles`.

Origin Adapted from Caveman (MIT).

router

Sinter's entry point. Use at the start of ANY software task to select a depth lane (lazy, standard, full) before doing work, and to re-check the lane when the task turns out bigger or smaller than it looked. Also fires when the user says "sinter", "/build", or asks which mode is active.

Fires on any request to write, fix, add, change, refactor, review, plan, debug, optimize, or ship code, including a thin or vague one - it routes through `clarify` first when the request is too unclear to lane.

Not for non-software requests, or for follow-up turns inside a lane that is already set and still correct.

Understand5

Before any edit. Reading the repository, tracing the real flow, and checking documentation rather than recalling an API.

codebase-onboarding

Use when meeting an unfamiliar repository, or when the user asks how a system works, wants a walkthrough, or is joining a project. 0).

Fires on "explain this codebase", "how does X work", "onboard me", "give me a tour", "draw the architecture".

Not for tracing a single change - that is `understanding-first`.

Origin Merges ECC codebase-onboarding, code-tour, repo-scan and ClosedLoop mermaid-visualizer (MIT / Apache-2.

docs-lookup

Use before stating how a library, framework, API, or tool behaves - versions, signatures, configuration, defaults, deprecations. Fires when the user names a framework or asks about setup or an API. Prevents recalled-from-training APIs that no longer exist.

Origin Adapted from ECC documentation-lookup (MIT).

inherit-legacy-style

Use when working in an existing codebase whose conventions differ from mainstream idiom, especially hand-written or long-lived projects. Prevents style drift.

Fires on legacy code, unusual project structure, and when a change would introduce a pattern the codebase does not use.

Origin Adapted from ECC (MIT).

iterative-retrieval

Use when a codebase is too large to read and a question needs an answer from it. 0).

Fires on searching large monorepos, "where is X handled", "find all places that Y".

Origin Adapted from ClosedLoop (Apache-2.

understanding-first

Use before editing any code you did not just write. Traces the real flow, finds every caller, and identifies what a change will touch. Enforces invariant 1.

Fires on any modification request against existing code.

Not for greenfield files with no callers.

Plan5

Turning an idea into agreed, testable work - and dispatching it.

brainstorming

Use before any creative or greenfield work - new features, new components, new services - to turn an idea into an agreed design before code exists.

Fires on "I want to build", "how should I approach", "help me design".

Not for bug fixes or small changes to existing behavior.

Origin Adapted from Superpowers (MIT).

executing-plans

Use when a written plan exists and implementation is starting. Governs phase order, gates, and state. 0).

Fires on "execute the plan", "start implementation", "continue the plan".

Origin Adapted from Superpowers (MIT) and ClosedLoop (Apache-2.

subagent-dispatch

Use when work can be split across parallel agents, or when a task needs a fresh context window.

Fires on multi-file review, independent plan tasks, and large refactors.

Not for work with sequential dependencies.

Origin Adapted from Superpowers (MIT).

writing-plans

Use when work needs a plan before implementation - full lane, multi-phase work, or when the user says "plan this". Produces plan.json (canonical, gated) and PLAN.md (human-readable, editable), which round-trip. 0).

Origin Adapted from Superpowers (MIT) and ClosedLoop (Apache-2.

writing-specs

Use when turning an agreed design into testable acceptance criteria, or when the user provides a PRD, spec, or requirements document. Produces the input the plan and the judges verify against.

Fires on "write the spec", "acceptance criteria", "requirements".

Build7

Writing the thing, and the disciplines that keep it correct while you do.

api-design

Use when designing or reviewing an HTTP, GraphQL, or RPC interface, or changing an existing one.

Fires on "design an API", "REST endpoint", "GraphQL schema", "versioning", "should this be a POST".

Origin Adapted from ECC api-design (MIT) and directives by @hollyos.

architecture

Use when designing systems, defining module boundaries, deciding where code belongs, or evaluating coupling.

Fires on "how should I structure", "architecture", "should this be a separate service", "where does this belong".

Not for single-function design.

Origin Adapted from ECC hexagonal-architecture (MIT) and directives by @hollyos.

data-acquisition

Use when a project needs data from outside it - scraping, third-party APIs, bulk imports, ETL.

Fires on "scrape", "pull data from", "import this dataset", "ETL", "crawl".

database

Use when designing schemas, writing or reviewing migrations, or diagnosing query behavior. Migrations are the highest-risk routine operation in software - always at least standard lane.

Fires on "migration", "schema", "add a column", "this query is slow", "index".

Origin Adapted from ECC database-migrations (MIT).

simplification

Use after implementation is working, before review, to apply the ladder to code that already exists.

Fires on "simplify", "clean this up", "reduce this", "too complex", and automatically at phase 4 in full lane.

Origin Adapted from Ponytail (MIT).

systematic-debugging

Use when encountering any bug, test failure, crash, or unexpected behavior, BEFORE proposing a fix.

Fires on "it's broken", "this fails", "why doesn't this work", stack traces, error messages, flaky tests, and performance regressions.

Not for feature work with no defect involved.

Origin Adapted from Superpowers (MIT), Ponytail (MIT), and directives by @hollyos.

test-driven-development

Use when implementing any feature or bugfix, before writing implementation code. Governs test policy across all lanes.

Fires on "write a test", "add tests", "TDD", and on any implementation request in standard or full lane.

Not for to decide WHICH kind of test to write - see `qa` for the test-type taxonomy.

Origin Adapted from Superpowers (MIT), with lane-bound relaxation.

Quality6

Attributes that are cheap to build in and expensive to retrofit.

accessibility

Use when building or reviewing any user interface - web, native mobile, or desktop. Owns accessibility testing. 0); a11y is semantics, not aesthetics.

Fires on "accessible", "a11y", "WCAG", "screen reader", "keyboard navigation", "contrast", and on any component work.

Origin Promoted from the Impeccable design lens (Apache-2.

analytics-instrumentation

Use when adding product analytics, event tracking, or measurement to an application.

Fires on "track this event", "analytics", "instrumentation", "tracking plan", "PostHog", "GA4", "Segment".

Not for systems observability - that is `observability`.

load-testing

Use when verifying a system holds under concurrency - load, stress, soak, or spike testing, capacity planning, or SLO validation. Distinct from `performance`, which optimizes single-request speed.

Fires on "load test", "stress test", "how many users can we handle", "k6", "JMeter", "Locust", "capacity".

performance

Use when something is slow, or when optimizing. Requires measurement before change.

Fires on "slow", "optimize", "performance", "latency", "memory", "bundle size", "N+1".

Not for load and stress testing - that is `load-testing`.

Origin Merges ECC react-performance, latency-critical-systems (MIT).

qa

Use when planning what to test, triaging bugs, designing regression suites, or when a request names a test type - smoke, sanity, acceptance, integration, contract, exploratory, end-to-end, black-box, functional. Owns the test-type taxonomy.

Not for the red-green cycle itself - that is `test-driven-development`.

technical-seo

Use when building or reviewing web pages that need to be discoverable - marketing sites, docs, e-commerce, public content. Technical SEO only; content strategy is `stack-packs/product`.

Fires on "SEO", "meta tags", "sitemap", "structured data", "canonical", "why isn't this indexed", "Core Web Vitals".

Secure4

These fire on the surface, not on the request. If the code touches auth, input, secrets or money, they run.

attack-surface-recon

Use when mapping what an organization exposes publicly - subdomains, endpoints, storage buckets, leaked credentials, dependency provenance. Scoped to assets you own or are authorized to assess.

Fires on "attack surface", "what are we exposing", "shadow IT", "exposed secrets".

cryptography

Use when handling encryption, key management, TLS, hashing, signing, or tokens. Prevents the most consequential class of self-inflicted security bug.

Fires on "encrypt", "hash", "sign", "JWT", "TLS", "certificate", "key rotation", "at rest".

penetration-testing

Use when actively probing a system for exploitable weaknesses - authorization bypass, injection, fuzzing, OWASP Top 10 verification. Requires ownership or written authorization for the target.

Fires on "pen test", "can this be exploited", "try to break in".

security-review

Use when writing or reviewing authentication, authorization, input handling, secrets, file uploads, payments, or any endpoint exposed to untrusted input. Fires proactively on those surfaces, not only when asked.

Not for active exploitation - that is `penetration-testing`.

Origin Adapted from ECC security-review (MIT).

Ship6

Proving it works, getting it out, and keeping it working.

finishing-a-branch

Use when work is complete and ready to commit, or when preparing a PR. Enforces the autonomy level.

Fires on "commit this", "open a PR", "wrap this up", "ship it".

Origin Adapted from Superpowers (MIT).

git-worktrees

Use when work needs isolation from the current checkout - parallel features, risky refactors, reviewing a branch while keeping your own work.

Fires on "worktree", "work on this separately", "without touching my branch".

modernization

Use when upgrading dependencies, migrating frameworks or major versions, handling deprecations, or working on legacy code deliberately.

Fires on "upgrade", "migrate to", "deprecated", "end of life", "modernize", "port this".

Not for incidental cleanup during unrelated work - see `inherit-legacy-style`.

observability

Use when adding logging, metrics, tracing, or alerts, or when diagnosing a production issue. For the EU regulation DORA see `compliance`, not this skill.

Fires on "logging", "metrics", "tracing", "alert", "monitoring", "we can't see what happened", "DORA metrics".

release

Use when setting up CI/CD, deploying, planning a rollout, or handling a rollback.

Fires on "deploy", "release", "CI", "pipeline", "rollback", "canary", "feature flag", "ship it".

verification-before-completion

Use before claiming any work is complete, fixed, passing, or done, and before committing, pushing, or opening a PR. Requires fresh evidence for every claim.

Fires on "done", "fixed", "works now", "tests pass", "ready to ship".

Origin Adapted from Superpowers (MIT).

Review4

Reading a change critically - automated, human, and against a rubric.

compliance

Use when work touches a regulated framework - SOC 2, ISO 27001, ISO 42001, GDPR, HIPAA, DORA, FedRAMP, CMMC, PCI-DSS, or accessibility law. Assesses technical controls and produces evidence. Does NOT certify.

Fires on those names, on "audit", "controls", "evidence", and proactively when code touches PII, PHI, cardholder data, or audit logging.

Origin Generalized from ECC hipaa-compliance (MIT).

judges

Use at quality gates in full lane, or when explicitly asked to evaluate an artifact against a rubric. Eight consolidated rubrics score plans, specs, and code. 0), consolidated from 22 agents to 8.

Not for line-by-line review - that is `review-engine`.

Origin Adapted from ClosedLoop judges (Apache-2.

receiving-review

Use when responding to review feedback - from a human, from Sinter, or from a tool.

Fires on "address these comments", "the reviewer said", "fix the review findings".

Origin Adapted from Superpowers (MIT).

review-engine

Use when reviewing a diff, a pull request, or a set of changes. Partitions the diff, runs deterministic checks first, spawns specialist reviewers, verifies findings before reporting. 0).

Fires on "review this", "code review", "look at this PR", and automatically at phase 5 in full lane.

Origin Adapted from ClosedLoop code-review (Apache-2.

Write it down2

The parts of engineering that are prose.

technical-influence

Use when a technical decision needs buy-in - RFCs, migration proposals, making the case for paying down debt, incident communication, or explaining a tradeoff to non-engineers.

Fires on "write an RFC", "convince", "how do I justify", "explain to leadership", "postmortem".

writing-docs

Use when writing READMEs, API documentation, changelogs, ADRs, runbooks, or code comments.

Fires on "document this", "write a README", "changelog", "ADR", "explain this for the docs".

Surfaces5

Whole areas of work with their own vocabulary.

authoring

Use when writing or improving skills, agents, commands, or hooks - for Sinter or for another plugin. 0).

Fires on "write a skill", "create an agent", "add a command", "plugin".

Not for building agent products - that is `stack-packs/agent-engineering`.

Origin Merges Superpowers writing-skills and ClosedLoop platform (MIT / Apache-2.

autonomy

Use when running unattended iteration over specs or a plan. Defaults to committing locally and never pushing.

Fires on "run the loop", "work through the specs", "keep going until done", "/sinter:loop".

Origin Adapted from Ralph Wiggum (MIT).

design

Use when building or improving user interfaces, or when the user asks for design work - critique, polish, layout, typography, color, motion, or hardening empty and error states. 0).

Fires on "make this look better", "design review", "UI feels off", "polish this".

Not for accessibility - that is `accessibility`.

Origin Adapted from Impeccable (Apache-2.

memory

Use when capturing a durable lesson about a codebase or workflow, or when loading past learnings at session start. 0).

Fires on "remember this", "note for next time", and automatically at session start and after gate failures.

Origin Adapted from ClosedLoop self-learning (Apache-2.

self-improvement

Use to turn recurring patterns in captured learnings into concrete, reviewable improvement proposals - a skill edit, a new project convention, a pack rule. It only ever PROPOSES. A human reviews and merges. Reworks the capture/learn loop from ClosedLoop self-learning (Apache-2.0) into a propose-only cycle.

Fires on "what could be better", "any patterns", "improve yourself", "/sinter:improve", and runs opportunistically when `memory` captures a learning that echoes earlier ones.

Not for to apply changes to skills, config, or instructions automatically - see "The boundary" below.

Stack2

Choosing which ecosystem knowledge to load, and what to do when there is none.

language-agnostic

Use when working in a language or ecosystem with no curated stack pack. Fires automatically when `stack-detect` finds no match. Derives conventions from the repository and official documentation instead of curated knowledge, and says so.

stack-detect

Use at the start of work in a repository to identify its stack and load the matching packs. Fires at session start, on `/sinter:init`, and when work moves into an unfamiliar part of a repository. Falls back to `language-agnostic` when no pack matches.
