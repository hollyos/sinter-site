Commands

Fifteen commands in one namespace. They are thin dispatchers: a command routes to skills and parses arguments; it never holds the behaviour itself.

In detail

Write code5

The main entry and the paths into it.

/sinter:build

[--lane lazy|standard|full] <what to build>

Main entry. Implement, fix, or change code. Routes by depth lane.

Route to router first. It selects the lane and states it in one line.

Then, per lane:

  • lazy - understanding-first, then principles ladder. One runnable

check if the logic is non-trivial.

  • standard - understanding-first, test-driven-development (red/green),

principles correctness bar. State tradeoffs.

  • full - hand off to /sinter:plan. Do not implement before the gate.

Load stack packs via stack-detect. If no pack matches, language-agnostic

and say which tier.

--lane overrides inference. Escalation rules in router still apply and

still announce themselves.

/sinter:plan

[--from <spec|PRD path>]

Write an implementation plan. Full lane. Stops at the human gate.

  • understanding-first, and codebase-onboarding if the repo is unfamiliar
  • writing-specs if acceptance criteria do not exist yet
  • writing-plans - produces plan.json and PLAN.md
  • judges on spec-quality and grounding
  • Stop. Present the plan. Wait for approval.

Do not implement. The gate is the point of this command.

/sinter:amend

<what changed>

Modify an approved plan through conversation.

Load plan.json. Apply the change through writing-plans conventions.

Regenerate PLAN.md. Preserve completed-task state.

Re-run judges on grounding and completeness if the change is structural.

Report what moved, what was added, what was dropped.

/sinter:debug

<symptom or error>

Systematic debugging. Root cause before any fix.

Route to systematic-debugging. All four phases, in order.

Do not propose a fix before phase 1 produces a one-sentence mechanism

statement. If the root cause lands in a shared function, router escalates -

say so.

/sinter:audit

[--scope <path>] [--debt|--dead|--simplify]

Simplification, dead code, and technical debt.

Route to simplification for working code.

  • --simplify (default) - apply the ladder to existing code
  • --dead - unreferenced exports, unreachable branches, unused dependencies
  • --debt - inventory with cost framing for technical-influence

Behavior-preserving. Anything that changes behavior is a separate change with

its own tests. Invariant 4 binds - validation, error handling, security, and

accessibility are not removable.

Review3

Reading a change, then acting on what was found.

/sinter:review

[--depth shallow|deep] [--pr <n>] [--since <ref>]

Multi-agent code review of a diff or PR.

Route to review-engine.

Default scope: uncommitted changes, then the current branch against its base.

--since overrides. --pr fetches the PR diff and posts inline comments.

--depth shallow runs hygiene and the correctness reviewer only. deep adds

cross-file, security, tests, and conventions reviewers.

If any changed file touches a controlled surface, compliance runs in

continuous mode and its findings are included.

/sinter:fix

[--severity blocking|high|medium|all]

Act on findings from a prior review.

Load findings from the last review-engine run.

Verify each finding still applies before acting on it - the code may have

changed. Fix in severity order. Each fix follows the lane's test policy.

Re-run verification-before-completion before reporting. Report what was

fixed, what was deliberately not, and why.

/sinter:comply

<framework...> [--evidence]

Assess technical controls against a framework and export evidence.

Route to compliance.

Frameworks: soc2, iso27001, iso42001, gdpr, hipaa, dora, fedramp, cmmc, pci.

  • Retrieve current control text (docs-lookup) - never assess from memory
  • Run scripts/assess.mjs deterministic checks
  • Map results through controls/crosswalk.json
  • Report per control: met, gap, needs-human-evidence, or not-assessable

--evidence exports the artifact bundle.

Every report states the boundary: Sinter assesses, it does not certify. A

control is never met on inference.

Design1

Frontend work with its own vocabulary.

/sinter:design

<lens> [target]

Frontend design work - critique, polish, layout, motion, hardening.

Route to design. Lens is one of: critique, polish, distill, bolder, quieter,

layout, typeset, colorize, animate, harden, delight.

Reads PRODUCT.md and DESIGN.md if present; asks audience and brand-vs-product

if not.

Runs scripts/detectors.mjs first - deterministic, no model.

Accessibility findings route to accessibility and are not styling

preferences.

Run unattended1

Iteration without you in the loop.

/sinter:loop

[--level propose|commit|autonomous] [--max <n>]

Run unattended iteration over specs or a plan.

Route to autonomy.

Default level commit - commits locally, never pushes. --level overrides

for this run only; persist it in sinter.config.json if it should stick.

autonomous requires an explicit branch target and will refuse without one.

Runs in a worktree at commit and autonomous. Halts on the conditions in

autonomy. Rails in hooks/pre-tool-use.sh bind at every level.

Set up & control5

Configuration, memory, and finding your way around.

/sinter:init

[--scaffold-pack] [--design]

Bootstrap Sinter in a repository.

  • stack-detect - identify ecosystems per workspace
  • codebase-onboarding - architecture map, conventions, entry points
  • Write sinter.config.json with detected defaults
  • Write or update CLAUDE.md / AGENTS.md with project conventions
  • --design also writes PRODUCT.md and DESIGN.md (design)
  • --scaffold-pack writes a tier-3 pack to .sinter/packs/ for an ecosystem

with no curated pack

Idempotent. Re-running updates rather than duplicating.

/sinter:mode

[lane auto|lazy|standard|full] [build lite|full|ultra] [prose normal|tight|terse] [autonomy propose|commit|autonomous]

Set lane, dials, and autonomy level.

No arguments: report the current settings and where each came from

(inline, session, project config, user config, or default).

Session-scoped unless written to sinter.config.json.

Resolution order:

inline flag > session /mode > ./sinter.config.json > ~/.sinter/config.json > defaults

/sinter:learn

[capture <text> | list | prune | scope <none|project|user|team>]

Capture, review, or prune learnings.

Route to memory.

capture applies the four-part quality bar before writing - durable,

non-obvious, actionable, specific. Rejections say which test failed.

prune removes stale, contradicted, never-triggered, and duplicate entries.

Run it periodically; an unpruned store silently degrades every session.

/sinter:help

[skill or topic]

What Sinter can do, and when each part fires.

No arguments: the command surface, the current lane and dials, and the loaded

stack packs.

With an argument: what that skill does, when it fires, and what it explicitly

does not cover.

With ~48 skills, this is not a nicety - a capability nobody can find is a

capability that does not exist.

/sinter:stats

[--by skill|agent|phase]

Token and cost attribution for this session.

Reads the session transcript. Reports tokens and estimated cost by skill,

agent, or phase.

Useful for tuning judges.routing and finding a reviewer fleet that costs

more than it returns.
