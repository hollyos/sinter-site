Modules

Every skill, pack, and agent ships inside the one Sinter plugin. Modules are logical groups the router pulls into scope on demand, so you get the breadth without assembling a setup. There is nothing to install and nothing to configure per session.

Zero setup

The core module is always on. Every other module defaults to auto: dormant until a task matches it, then in scope for that task. You never pick modules before you start working. Describe the task and the router brings in what it needs.

How activation works

  1. Core is always in scope the lifecycle skills and always-on surfaces.
  2. The router reads the task after it sets a depth lane, it matches the request against each module's trigger keywords.
  3. Matching modules come into scope their skills become eligible to fire. A task can pull in more than one.
  4. Announced in one line only when it changes what happens. Unused modules stay silent.

Pinning, when you want it

Auto needs no configuration. To force a module always on, or always off, set it in sinter.config.json under modules, or for the session with /sinter:modules.

CommandEffect
/sinter:modules listShow every module and its current state
/sinter:modules on networkingKeep a module in scope for every task this session
/sinter:modules off mediaKeep a module out of scope even when a task matches
/sinter:modules auto complianceReturn to the default on-demand behaviour
A module is scope, not new rules

Bringing a module into scope does not change the lane, the dials, the invariants, or the autonomy level. It only decides which skills are available. The behaviour lives in the skills, exactly as it does without the module layer.

The access module never auto-activates

The access module holds the reader-accessibility profiles. It is turned on only when you ask, with /sinter:access. Sinter never infers it.
